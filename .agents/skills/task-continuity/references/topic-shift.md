# 话题切换判断协议

本协议用于判断一条新消息是在继续当前 Task、讨论相关支线，还是启动另一项
Task。Task 与 Conversation 是两个概念：一个会话可以容纳多个 Task，一个 Task
也可以跨多个会话。不得把“新会话”直接等同于“新任务”，也不得把“同一会话”
直接等同于“同一任务”。

## 1. 三类结果

### CONTINUE

消息直接推进当前目标或当前交付物，例如实现下一步、修复当前缺陷、补全当前
设计。正常执行，不提示切换会话。

### TANGENT

消息不是当前交付物本身，但服务于当前任务，例如解释当前代码涉及的概念、
比较当前方案的两个选项、回答会影响下一步的小问题。回答支线，同时保持当前
Task 为 Active；不提示新会话。

### SWITCH

消息的项目、目标、交付物或意图与当前 Task 明显不同，需要独立上下文和后续
步骤。切换前应先对当前 Task 做必要 checkpoint。

## 2. 多维判断

不要只依赖关键词、主题相似度或单个实体。综合检查：

- **Project Identity**：是否仍属于同一项目或工作域；
- **Goal**：用户最终想达成的结果是否相同；
- **Deliverable**：要产出的文件、功能、报告或决定是否相同；
- **Artifact**：正在操作的仓库、路径、文档、接口或数据是否相同；
- **Entity**：关键对象是否与当前任务存在实际关系；
- **Current Phase**：消息是否属于当前阶段的输入、依赖或验收；
- **User Intent**：是在询问、修改、暂停、恢复，还是开启独立工作。

判断顺序：

1. 先识别用户意图以及期望交付物。
2. 再与当前 Task Contract 和 Current State 比较。
3. 若消息直接推进当前目标，判为 `CONTINUE`。
4. 若消息能帮助当前任务但不改变其身份，判为 `TANGENT`。
5. 只有多个核心维度明显分离，且需要独立工作链时，才判为 `SWITCH`。

如果仍有合理歧义，优先按 `TANGENT` 处理短问题；不要为了分类而打断用户。
若错误分类会导致写入错误项目、改动错误文件或改变任务契约，则先用一句话确认。

## 3. 常见易混场景

- 关键词相同不代表同一意图：“QUIC 是什么”通常是当前网络任务的 Tangent；
  “把第一阶段改成 QUIC”是当前 Task 的重大变更，应更新契约和 Decision，但
  仍不一定是 SWITCH。
- 文件不同不必然是 SWITCH：同一功能所需的测试、文档和实现可以属于一个 Task。
- 项目相同不必然是 CONTINUE：在同一仓库中启动独立模块或独立交付物，可能是
  SWITCH。
- 简短无后续的生活问题或工具解释可直接回答；不必建立 Task，也不必提示新会话。
- “继续刚才的内容”需要根据 Task ID、目标、制品和最近状态解析，不要仅按最近
  一条消息猜测。

## 4. 何时提醒新会话

只有同时满足以下条件时，才建议用户考虑新会话：

1. 当前存在 Active Task；
2. 当前 Task 已形成明显上下文或有待恢复的后续工作；
3. 新消息被判定为 SWITCH；
4. 新任务预计不是一句话即可结束，而是会形成自己的工作链。

提醒前先 checkpoint 当前 Task。提示应简短、非强制，并说明当前状态已保留，
例如：

> 当前内容已从「现有任务」切换到一项新的长任务。为避免两边上下文互相污染，
> 可以考虑新开会话继续；当前任务状态已保留。

如果用户选择留在当前会话，正常执行，不反复提醒。Skill 不得擅自创建新会话。

## 5. 切换时的最小动作

确认 `SWITCH` 后：

1. 若旧 Task 有未记录的实质进展，更新其 HANDOFF；
2. 保留旧 Task 的目标、未解 Blocker 和 Next Actions；
3. 不把新任务内容写进旧 Task 的记忆目录；
4. 为新任务解析 Project、Goal、Deliverable 和 Artifact；
5. 一次性问题无需建档；若新任务需要持续状态，先确定不会覆盖旧任务的独立记忆
   归属，再建立新的 Task Contract。MVP 未定义多 Task 存储布局时，不得自行发明
   路径或覆盖现有 HANDOFF。

## 6. Task Stack：仅限 Phase 2 的可选能力

MVP 不要求 Task Stack。默认做法是一次只维护一个明确的 Active Task，并通过
各项目或任务的 HANDOFF 恢复旧任务。

只有用户选择在同一会话持续处理多个长任务，且运行环境能够稳定区分它们时，
才可以启用：

```text
Active Task
Paused Tasks
```

启用后仍须遵守：

- 每个 Task 使用独立 Task ID 和独立记忆归属；
- 任一时刻只允许一个 Active Task；
- 暂停前 checkpoint，恢复时先读取该 Task 的 HANDOFF；
- 不因会话顺序自动合并 Task；
- 用户说“继续之前的任务”但候选不唯一时，先确认具体 Task；
- Task Stack 只记录激活关系，不复制各 Task 的完整记忆。

不要为了实现 Task Stack 引入数据库、后台服务或自动任务调度。若当前项目只需要
Phase 1 的基本连续性，完全不创建 Active / Paused 结构。
