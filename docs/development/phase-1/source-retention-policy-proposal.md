# File Source 恢复记录保留策略

状态：保留期与起算事件已接受（D-015，2026-09-04）。承接source-retention-preflight.md；清理接口及实施另行确认。

## 已接受的保留策略

| 记录 | 最短保留期 | 起算字段 |
|---|---|---|
| File processing receipt | 30 × 24小时 | committed_at_us |
| Retired File generation | 30 × 24小时 | retired_at_us |

30天是用户接受的产品策略，不是现有配置值、行业保证或由负载测量推导出的最优值。
选择同一时长便于理解，并为调查与诊断保留一个月的最短观察窗口；不据此承诺保留完整日志或诊断链。
两类记录分别起算，不承诺整个代际在30天内清理。由于恢复及外键保护，实际保留可能更久。
尚无实际投递率和存储预算证据，本方案不承诺磁盘占用上界；实施前若需硬空间目标，应单独评估。

使用已有持久时间字段，不新增checkpoint越过时间。receipt达到年龄要求后，
仍须在清理时证明checkpoint已经持久安全越过；不是从安全越过后再等待30天。
generation只在实际退休后开始计时，不能按opened_at或sealed_at代替。

## 到期与安全资格设计约束

每次操作取得一个UTC截止快照；时间精度与数据库微秒一致。
当记录时间小于或等于now减去30天时，仅成为年龄候选；缺失、非法或未来时间不得取得资格。
时间来源及系统时钟大幅前跳的处置须在API设计阶段明确，本方案不声称具备抗时钟跳变保证。

真正删除前，在同一事务内重新核对：

1. receipt的稳定Position已被持久且不会回退的恢复边界安全越过；跨session不得直接比较Sequence。
2. generation只有Retired且无checkpoint、receipt及当前恢复依赖时才有删除资格。
3. 任何现有业务外键仍引用候选，均保守保留；不级联删除Parser结果、检测贡献、Alert、Decision或Audit。
4. 事务失败或取消不产生部分删除；重试不能扩大目标集合或绕过资格检查。

保留期不是绕过恢复保护的期限。既有处理结果外键可能使大量receipt长期保留；
本阶段不承诺回收所有到期空间，也不以放宽外键解决保留问题。

## 下一设计单元

下一步先定义有限File清理原语的具体接口、事务边界及验收测试，再取得接口实施授权。
必须证明receipt删除后迟到的旧投递不会重新计数，以及generation删除后旧身份不会被恢复路径错误重建。
这些约束要结合现有处理所有者、持久恢复边界与外键判断，不能只靠调用方传入安全布尔值。
若现有机制无法证明某候选安全，则继续保留并列明阻塞，不预设新增持久模型。
